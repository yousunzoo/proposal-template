# 포트폴리오 제안서 제품화 로드맵

작성일: 2026-09-03

## 1. 방향

`proposal-template`은 외부 관리 시스템으로 이관 후 폐기하는 프로토타입이 아니라, 포트폴리오 제안서 생성을 위한 독립 제품 프로토타입으로 유지한다.

제품의 핵심 가치는 다음 3가지다.

1. 제안서 원문을 구조화해 읽기 좋은 공개 제안서 페이지로 만든다.
2. 프로젝트 성격에 맞는 포트폴리오를 추천하고, 제안서 안에서 근거 자료로 연결한다.
3. 발행 링크와 PDF를 통해 외부 고객에게 전달 가능한 산출물을 만든다.

따라서 앞으로의 고도화는 단순한 내부 도구 정리가 아니라, "민감정보를 제거한 재사용 가능한 제안서/포트폴리오 생성 제품"으로 가는 방향이어야 한다.

## 2. 민감정보 폐기 원칙

### 2.1 폐기 대상

소스와 기본 데이터에서 제거하거나 익명화해야 할 항목:

- 실명 팀원 정보: 기본 팀 소개에 들어간 개인 이름과 영문 이름
- 회사 식별 정보: 특정 회사명, 내부 브랜드명, 연락처 노출 가능 문구
- 고객사/서비스명: 공개 사용 허가가 없는 고객사명, 내부 프로젝트명, 실제 운영 서비스명
- 정량 지표: 누적 사용자 수, 월 방문자 수, 계약 금액, 개발비 등 검증/공개 승인 없는 수치
- URL: 고객사 운영 URL, 내부 도메인, 비공개 접근이 필요한 링크
- 환경값: `.env.local`, API key, DB URL, 인증 비밀번호, 세션 시크릿
- 생성 원문: 발주처 RFP, 견적, 예산, 일정, 요구사항 원문 중 비공개 정보

### 2.2 유지 가능한 정보

민감정보를 제거한 뒤에도 제품 가치를 유지하기 위해 다음 정보는 구조만 남긴다.

- 도메인: 금융, 커머스, 교육, 지도, 예약, AI 챗봇 등
- 문제 유형: 관리자 CMS, 매칭 플랫폼, 예약 시스템, 퍼블리싱, 접근성 개선 등
- 기술 범주: 프론트엔드, 백엔드, 인프라, 데이터 마이그레이션, QA
- 성과 표현: "대규모 트래픽 대응", "운영 업무 자동화", "검색/필터 개선"처럼 수치 없는 범주형 표현
- 역할 구성: PM, 기획, 디자인, 프론트엔드, 백엔드처럼 개인명이 없는 직무 단위
- 포트폴리오 사례: 실제 고객명이 아닌 익명 케이스 스터디

### 2.3 폐기 방식

민감정보 폐기는 삭제와 익명화를 구분한다.

- 기본 회사/팀 소개: 삭제가 아니라 "벤더 프로필 템플릿"으로 치환
- 포트폴리오 제목: 실명 서비스명 대신 익명 케이스명으로 치환
- 포트폴리오 본문: 공개 가능한 문제/해결/성과 구조만 남기고 고유명사 제거
- 이미지: 고객 로고, 실제 서비스 UI, 식별 가능한 스크린샷은 플레이스홀더나 추상화된 목업으로 교체
- 문서: 기존 이관 문서는 보존하되, 현재 제품 방향과 충돌하는 부분은 별도 제품화 문서에서 명시적으로 대체
- 환경값: `.env.local`은 계속 git ignore 상태 유지, 예시는 가짜 값만 보관

## 3. 현재 코드 기준 리스크

### 3.1 기본 콘텐츠에 민감정보가 포함됨

`packages/shared/src/index.ts`의 기본 회사 소개와 팀 소개에는 실명, 특정 서비스명, 운영 지표가 들어 있다. 독립 제품으로 유지하려면 기본값에서 제거해야 한다.

권장 변경:

- `DEFAULT_ABOUT_INTRO`: 특정 회사/서비스/수치 제거
- `DEFAULT_TEAM_GROUPS`: 개인명 제거, 역할 기반 기본값으로 교체
- `DEFAULT_TEAM_BULLETS`: 인원/경력 등 검증 필요한 수치 제거 또는 사용자 입력값으로 분리

### 3.2 정적 포트폴리오 데이터가 실서비스 중심임

`apps/web/src/entities/portfolio/constants/*`는 실제 서비스명과 상세 설명을 다수 포함한다. 제품 프로토타입으로 유지하려면 "샘플 포트폴리오 라이브러리"로 재정의해야 한다.

권장 변경:

- 실명 서비스 기반 사례 파일을 익명 케이스명으로 교체
- URL이 포함된 항목 제거
- 고객 식별 가능한 썸네일/상세 이미지를 제품용 목업 이미지로 교체
- `Project` 타입에 `confidentiality` 또는 `visibility` 필드를 추가해 공개 가능 여부를 명시

### 3.3 입력 검증이 타입 수준에 머묾

API route는 `req.json()` 결과를 그대로 서비스 계층에 전달한다. 운영 가능한 제품이 되려면 `CreateProposalInput`, `UpdateProposalInput`, `ProposalSectionsData`의 런타임 검증이 필요하다.

권장 변경:

- `packages/shared`에 Zod 스키마 추가
- API route에서 schema parse 후 서비스 호출
- 잘못된 섹션 구조는 저장하지 않도록 차단

### 3.4 AI 구조화 결과 검증이 부족함

AI 구조화 실패 시 결정론 파서로 폴백하는 구조는 좋지만, 결과 품질을 측정하지 않는다.

권장 변경:

- 생성 결과에 `parserMode`: `ai` 또는 `deterministic` 저장
- 프롬프트 버전과 모델명 저장
- 누락 감지 체크: 원문 주요 문장/금액/기간/고유명사 보존 여부
- 발행 전 품질 체크리스트 제공

## 4. 핵심 기능 고도화 로드맵

### P0. 제품 기준 재정의

목표: 민감정보 없이도 데모와 개발이 가능한 제품 기준을 만든다.

작업:

- 기존 `docs/migration-to-admin-fe.md`는 과거 이관 계획으로 보존
- README에 "독립 제품 프로토타입 유지" 방향 반영
- 기본 회사/팀/포트폴리오 데이터를 익명 샘플로 교체
- `.env.example`은 유지하되 실제 값이 아닌 placeholder만 허용
- 민감정보 스캔 명령을 문서화

게이트:

- `rg`로 실명, 고객사명, 실제 URL, 키 패턴이 검출되지 않아야 함
- `pnpm build` 통과

### P1. 데이터/검증 안정화

목표: 잘못된 제안서 문서가 DB에 저장되지 않게 한다.

작업:

- `ProposalSectionsData` Zod 스키마 도입
- `CreateProposalInput`, `UpdateProposalInput` 런타임 검증
- Prisma 문자열 JSON 컬럼을 `Json` 컬럼으로 전환 검토
- slug 생성에 `crypto.randomUUID()` 또는 `nanoid` 사용
- 저장 전 `normalizeDoc` + schema 검증 수행

게이트:

- 생성/수정/발행 API에 잘못된 payload를 넣었을 때 400 응답
- 기존 샘플 문서가 정상 normalize

### P2. 포트폴리오 제품화

목표: 이 제품을 "제안서 생성기"가 아니라 "포트폴리오 기반 제안서 생성기"로 만든다.

작업:

- 포트폴리오를 정적 상수에서 관리 가능한 엔티티로 승격
- 포트폴리오 필드 확장:
  - 문제 상황
  - 수행 범위
  - 사용 기술
  - 도메인/플랫폼 facet
  - 공개 가능 여부
  - 제안서에 넣을 요약 문장
  - 익명화된 성과
- 원문 기반 포트폴리오 추천 점수 제공
- 선택 이유를 사용자에게 보여줌
- 제안서 섹션 안에서 포트폴리오별 근거 문장 자동 생성

게이트:

- 포트폴리오를 선택하지 않아도 추천 후보가 3개 이상 표시
- 추천 이유가 도메인/기술/기능 중 하나 이상과 연결됨

### P3. 제안서 편집 경험 고도화

목표: 생성 후 수동 보정 시간을 줄인다.

작업:

- 발행 전 체크리스트:
  - 제목 있음
  - 예산/기간 확인
  - 견적 비고 확인
  - 숨김 섹션 확인
  - 민감정보 검출 없음
- 섹션별 AI 재작성:
  - 전체 덮어쓰기 금지
  - 특정 섹션만 재정제
  - 변경 diff 확인 후 반영
- 문체 프리셋:
  - 간결형
  - 공공입찰형
  - 스타트업형
  - SI 수행계획형
- 섹션 템플릿 라이브러리:
  - 유지보수
  - 관리자 CMS
  - 커머스
  - 예약
  - AI 챗봇

게이트:

- 사용자가 전체 문서를 잃지 않고 섹션 단위로 AI 결과를 적용할 수 있음
- 발행 버튼 전에 경고/차단 조건이 명확히 표시됨

### P4. 공개 산출물 고도화

목표: 외부 고객에게 보낼 수 있는 제안서 링크와 PDF 품질을 높인다.

작업:

- 공개 링크 설정:
  - 공개/비공개
  - 링크 만료일
  - 비밀번호 보호
  - PDF 다운로드 허용 여부
- PDF 생성 안정화:
  - 비동기 생성
  - 생성 상태
  - 재시도
  - 캐시
- 인쇄 레이아웃 회귀 테스트
- 고객 열람 이벤트 기록:
  - 최초 열람
  - PDF 다운로드
  - 마지막 열람 시각

게이트:

- 같은 제안서의 PDF 재다운로드가 매번 Chromium을 띄우지 않아도 됨
- 공개 링크를 비공개로 바꾸면 즉시 접근 차단

### P5. 운영 제품화

목표: 개인 로컬 도구가 아니라 팀이 쓰는 제품으로 만든다.

작업:

- (현재 프로토타입은 인증 없음) 계정/역할 기반 인증 계층 신규 도입
- 제안서 목록/검색/복제/아카이브
- 버전 관리:
  - 생성 원문 버전
  - 섹션 편집 버전
  - 발행 스냅샷
- 감사 로그:
  - 생성
  - 수정
  - 발행
  - 비공개
  - PDF 생성
- Observability:
  - AI 실패율
  - PDF 실패율
  - 생성 시간
  - 발행 전 수정 횟수

게이트:

- 팀원이 여러 제안서를 관리해도 데이터 충돌과 추적 누락이 없음

## 5. 민감정보 제거 후에도 유지해야 할 제품 차별점

민감정보를 없애면 제안서가 빈 템플릿처럼 보일 위험이 있다. 이를 피하려면 "실명 사례" 대신 "구조화된 케이스 스터디"를 제품 자산으로 만들어야 한다.

권장 케이스 구조:

```ts
interface PortfolioCase {
  slug: string;
  title: string;
  summary: string;
  domain: string[];
  platform: string[];
  problems: string[];
  scope: string[];
  stack: string[];
  anonymizedOutcomes: string[];
  proposalEvidence: string[];
  visibility: 'public-sample' | 'internal-only' | 'draft';
}
```

이 구조를 쓰면 실제 고객명을 제거해도 제안서 생성에 필요한 근거는 유지된다.

예시:

- "실명 금융 서비스 | 대출 비교 플랫폼" → "금융상품 비교 플랫폼 구축 사례"
- "실명 금융 서비스 | 관리자 페이지" → "금융 운영 CMS 구축 사례"
- "고객 URL" → 제거
- "검증되지 않은 누적 사용자 수" → "다수 사용자 조건 검색을 고려한 구조"
- "팀원 실명" → "PM 1명, 기획 1명, FE 2명, BE 2명"

## 6. 추천 실행 순서

가장 먼저 할 일은 기능 추가가 아니라 민감정보 제거와 데이터 구조 보강이다.

1. 기본 콘텐츠 익명화
2. 정적 포트폴리오 익명 케이스화
3. 민감정보 스캔 스크립트 추가
4. Zod 검증 추가
5. 파서/AI fixture 테스트 추가
6. 포트폴리오 추천 이유 노출
7. 발행 전 민감정보/완성도 체크리스트
8. 공개 링크/PDF 운영 기능

이 순서가 맞는 이유는, 1~3을 하지 않으면 제품 데모 자체가 위험하고, 4~5를 하지 않으면 생성 품질을 고도화할 때마다 회귀를 감지하기 어렵기 때문이다.

## 7. 실행 기록

### 2026-09-03 P0 일부 완료

완료:

- 기본 회사 소개와 팀 소개를 익명 역할 기반 문구로 교체
- 정적 포트폴리오를 실명 사례 파일 묶음에서 익명 샘플 케이스 데이터셋으로 교체
- 포트폴리오 타입에 `visibility` 필드 추가
- 홈 화면 샘플 제안서에서 실제 이력처럼 읽히는 수치와 대표 사례 표현 제거
- 홈 화면 샘플 제안서를 지역 문화센터 강좌 예약·수강 관리 플랫폼 목업 도메인으로 교체
- 고객 식별 가능성이 있는 포트폴리오 이미지 자산 삭제
- 민감정보 스캔 명령 `pnpm sensitive:scan` 추가
- 과거 이관 계획 문서를 현재 방향과 충돌하지 않는 폐기 메모로 축소

검증:

- `pnpm sensitive:scan` 통과
- 고유명사 후보 스캔 통과
- `pnpm build` 통과

남은 P0/P1 후보:

- 저장된 DB 데이터에 기존 실명 사례가 있으면 별도 마이그레이션 또는 데이터 삭제 필요
- 배포 환경 스토리지와 Vercel 환경변수에 남은 민감정보 별도 점검 필요
