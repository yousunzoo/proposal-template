# 제안서 편집 화면 UX 리팩토링 — 설계

날짜: 2026-08-18
대상: `apps/web/src/app/proposals/[id]/edit/page.tsx` (1170줄 단일 파일)

## 배경 / 문제 진단

현재 편집 화면은 데스크톱 50/50 분할(좌 편집 / 우 프리뷰) 구조이며 다음 마찰이 있다.

1. 편집 영역이 화면 절반(xl 최대 560px)이라 중첩 리스트(팀 그룹→팀원) 편집이 답답하다.
2. 14개 아코디언 카드가 한 화면에 세로로 쌓여 스크롤 부하가 크다.
3. 표시/숨김 컨트롤이 카드 헤더·섹션구성 카드·점프 내비 3곳에 중복된다.
4. 저장 수단이 자동저장 + 상/하단 저장 버튼 + Cmd+S로 중복된다.
5. `RepeatList`가 `key={i}`를 써서 재정렬·삭제 시 입력 포커스/값이 꼬인다.
6. 프리뷰가 `pointer-events-none`이라 클릭 점프가 불가능하다.
7. 순서 변경이 ↑↓ 버튼뿐이다.
8. `AI 정제`가 `window.confirm` 하나로 전체를 덮어쓴다.
9. 배포 전 섹션 완성도 피드백이 없다.

## 목표

기존 구조를 재설계한다(사용자 승인). "포커스 단일 섹션 편집" 패러다임으로 전환한다.

## 새 구조 — 3-존 레이아웃

```
┌────────────┬────────────────────────┬──────────────┐
│ SECTION    │   [선택된 섹션] 편집     │  LIVE        │
│ RAIL       │   (넓은 단일 캔버스)     │  PREVIEW     │
│ ~260px     │   max ~720px            │  (토글)      │
│            │                         │              │
│ ▤ 프로젝트  │  섹션 제목               │  ProposalBody│
│ ▤ 인사말 ● │  ...필드...             │  활성 섹션    │
│▶▤ 전략  ●  │  리스트(드래그)          │  자동 스크롤  │
│ ▤ 견적  ○  │                         │  클릭→선택    │
│ ⋮ (drag)   │                         │              │
└────────────┴────────────────────────┴──────────────┘
```

### 1) Section Rail (좌, 단일 진실 원천)
- 상단 고정: `프로젝트 정보`(메타, 순서/표시 대상 아님).
- 그 아래 12개 콘텐츠 섹션: `framer-motion` `Reorder`로 드래그 재정렬.
  - 각 행: 드래그 핸들 · 라벨 · 완성도 점(● 채움 / ○ 비어있음) · 표시/숨김 눈 토글.
  - 활성 섹션 `bg-blue-50` 하이라이트, 숨김 섹션은 흐리게 + 취소선.
- 이 컴포넌트가 기존 "점프 내비 pill" + "섹션 구성 관리 카드"를 **완전 대체**한다.
- Reorder 값은 `layout.id`(안정 문자열) 사용.

### 2) Editor Canvas (중앙)
- 선택된 섹션 **하나만** 넓게 편집. `프로젝트 정보`도 하나의 편집 대상.
- 상단에 섹션 헤더(라벨 + 표시상태 + "프리뷰에서 보기" 링크).
- 섹션별 편집 폼은 `section-editors.tsx`에 분리.

### 3) Live Preview (우, 토글)
- 기본 off(2-존: 네비+편집으로 편집 폭 확보). 툴바 버튼으로 on/off.
- on일 때 활성 섹션으로 자동 스크롤.
- 섹션 클릭 시 해당 섹션 편집으로 전환(포인터 이벤트 부분 복원: 섹션 점프 용도).

## 저장 모델 정리
- 자동저장(디바운스 1.2s) + `Cmd/Ctrl+S` + 상태 pill 유지.
- 상/하단 중복 저장 버튼 제거. 툴바에 `배포`만 유지(+ 프리뷰 토글, 새 탭, AI 정제).
- 이탈 경고 유지.

## 리스트 키 버그 수정 (`key={i}` → 안정 키)
- `update()`가 매 편집마다 `structuredClone(doc)` 하므로 참조 기반 식별 불가.
- 해결: 클라이언트 전용 `_k` 필드를 리스트 항목 객체에 부여.
  - 로드시 `assignKeys(doc)`로 모든 객체 리스트 항목에 `_k` 주입(누락분).
  - 모든 `factory()`가 `_k: genKey()` 포함.
  - `structuredClone`이 `_k`를 보존 → 편집·재정렬 간 식별 안정.
  - `persist()`에서 `stripKeys(doc)`로 제거 후 저장(서버/프리뷰 오염 방지).
- `RepeatList` React key와 `Reorder.Item value`에 `_k` 사용.
- 순수 문자열 리스트(불릿/다짐/포함·미포함/소개 문단)는 드래그 없이 ↑↓ 유지, key는 `_k` 대신 안정 인덱스로 충분(추가/삭제만).

## 완성도 판정
- `_lib/completeness.ts`: `isSectionFilled(doc, id)` 휴리스틱.
- Rail의 점 색으로 표시. 숨김 섹션은 판정 제외(중립).

## AI 정제 안전장치
- `window.confirm` → 인라인 확인 상태(2단계 클릭) 또는 명시적 경고 문구 강화.

## 유지되는 계약
- 데이터 모델(`ProposalSectionsData`), API(`api.*`), 프리뷰 컴포넌트(`ProposalBody`)는 변경 없음.
- 저장 payload는 `_k` 제거된 순수 형태 유지.
